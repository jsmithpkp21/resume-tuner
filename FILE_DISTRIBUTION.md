# File Distribution for Managed Sync Contract

## Summary

This document explains which files are owned by the tooling repository, which
files are synced into consumer repos, and how the manifest + lock contract
controls that lifecycle.

## Source of Truth

Managed-file ownership is defined by two artifacts:
- `.tooling-sync-manifest.toml` at the root of this tooling repo — declares the desired set of files that may be synced
- `.tooling-sync-manifest.lock` in each consumer repo — records the managed files actually applied during the most recent successful sync

The manifest defines **what should be managed**.
The lock records **what is currently managed in that consumer**.

## Distribution Plan

### Files in `tooling/` repo

**Eligible for sync into projects:**
- Only files explicitly listed in `.tooling-sync-manifest.toml`
- Typical examples include shared docs, scripts, workflow helpers, and repo-wide config files
- Shared agent guidance such as `AGENTS.md` when present in the manifest
- Shared GitHub workflows under `.github/workflows/` when listed in the manifest
- Shared consumer-contract tests under `tests/scripts/` when listed in the manifest
- Shared workflow regression tests under `tests/workflows/` when listed in the manifest

**Tooling repo only (not auto-synced):**
- `scripts/sync_tooling.sh` — bootstrap/security-sensitive; consumers update this manually
- `pyproject.toml` — tooling-side config source, not copied directly into consumers
- `project-template/` — scaffolding for new projects only
- Any file omitted from `.tooling-sync-manifest.toml`

### Files in each consumer project

**Consumer-owned identity files (never synced):**
- `VERSION`
- `pyproject.toml` (generated from project metadata + tooling config)
- `.pyproject.meta.toml`
- `tooling.toml`
- `AGENTS_LOCAL.md` (optional local overrides/additions layered after `AGENTS.md`)
- `Makefile.local` (optional consumer-specific make targets loaded via `-include` from the synced `Makefile`)
- `docs/REFERENCE/IMPROVEMENTS.md` (consumer-local backlog/notes; explicitly not managed)
- `README.md`
- `CHANGELOG.md`
- `requirements.txt`
- `scripts/sync_tooling.sh`

`requirements.txt` has no tooling-managed sections under the Option A dev
requirements contract.

`requirements-dev.txt` is tooling-managed and synced to consumers as the shared
set of dev-tool dependencies used by `make setup`/`make verify` checks.

**Managed files synced from tooling:**
- Only files declared in `.tooling-sync-manifest.toml`
- After sync, those files are recorded in `.tooling-sync-manifest.lock`
- All managed files are subject to drift validation via `make drift-check`
- A subset of managed files are **post-sync template rewrites** — they are
  copied verbatim and then mutated in-place by `scripts/sync_tooling.sh` so the
  consumer ends up with consumer-specific content. See the next section for the
  exhaustive list.

## What `make drift-check` Actually Validates

`make drift-check` is a *consumer-side* check, not a tooling-source comparison.
It loads `.tooling-sync-manifest.lock` from the consumer repo, then for every
entry in `lock.files` it re-hashes the current consumer file with SHA-256 and
compares against the recorded hash. The check fails if any managed file has
been modified, deleted, or replaced with a symlink since the last successful
sync.

What this means in practice:

- **The reference is the lock, not the tooling source repo.** Drift-check has
  no knowledge of the current contents of the tooling repo; it only knows what
  was last applied. If the tooling source has moved on, that's a *re-sync*
  decision, not a drift failure.
- **The lock records post-mutation hashes.** `scripts/sync_tooling.sh` writes
  the lock *after* its post-sync rewrites (`.release-please-config.json`
  package-name, `scripts/merge_pyproject.py` regeneration, executable bits),
  so the recorded hash is the hash of the file as it sits in the consumer
  after sync — not the hash of the tooling-side template before mutation.
  Editing a template-mutated file in the consumer to "match the tooling
  source" will fail drift-check because the consumer's correct state is the
  *mutated* one.
- **`pyproject.toml` is consumer-owned and not in the manifest**, so it is
  *not* covered by drift-check at all. It is regenerated by
  `scripts/merge_pyproject.py` from `.pyproject.meta.toml`; the regeneration
  is a separate sync-time step, distinct from the manifest/lock contract.

## Synced Files With Post-Sync Mutation (Templates)

Most synced files are pure byte-for-byte copies. A small number are
intentionally **mutated after copy** so each consumer ends up with content
reflecting its own identity. Treat these as templates: edit the *template* in
the tooling repo, but understand that the consumer copy will diverge in a
structured, predictable way (and the lock will reflect the post-mutation
content).

| Synced file | Mutation applied in consumer | Source of truth for the mutation | Mutation guarantee |
|-------------|-------------------------------|----------------------------------|--------------------|
| `.release-please-config.json` | `packages["."]["package-name"]` is rewritten to the consumer's package name | `.pyproject.meta.toml` `project.name` (consumer-owned) | **Best-effort.** Requires Python 3.11+ on the sync host (uses `tomllib`); if Python is older or parsing fails, the script prints a warning and leaves the package-name as-is. Sync still succeeds; the consumer must hand-edit or re-sync from a Python 3.11+ host. |

(`pyproject.toml` is intentionally *not* in this table — see the previous
section. It is consumer-owned, regenerated rather than synced.)

**Implications:**

- If you add a new field to `.release-please-config.json` in the tooling
  source that should be consumer-specific, extend the rewrite block in
  `scripts/sync_tooling.sh` rather than committing a per-consumer value into
  the template.
- Adding a new template-mutated file to this set is a contract change —
  document it in this table (including its guarantee), update the rewrite
  logic, and add regression coverage in
  `tests/scripts/test_sync_tooling_regressions.py`.

**Existing regression coverage** for consumer identity preservation:

- `tests/scripts/test_sync_tooling_regressions.py` asserts that
  `.release-please-config.json` `package-name` is correctly rewritten to the
  consumer name after sync.
- `tests/scripts/test_consumer_contract.py` asserts that consumer-owned
  identity files (`.pyproject.meta.toml`, `VERSION`) are never overwritten
  by sync.

## Ownership Notes for Selected Synced Scripts

A few synced scripts have specific ownership rules worth calling out:

- **`scripts/validate_version_sync.py`** — synced *verbatim*, no template
  rewrite. Every consumer must enforce the same version-artifact alignment
  contract (`VERSION`, `pyproject.toml`, `.pyproject.meta.toml`,
  `.release-please-manifest.json` all on the same version). Consumers
  wanting different version-sync semantics must extend behavior via local,
  unsynced glue — for example a consumer-only Make target that wraps the
  validator with extra checks, or selective hook bypass via the standard
  pre-commit env var (`SKIP=version-sync-check git commit ...`) for
  intentional one-off cases. Do **not** edit the synced copy directly:
  changes will be reverted on the next sync.
- **`scripts/sync_tooling.sh`** — *not* auto-synced; consumers update it
  manually after review (see the dedicated section below).

## Managed File Lifecycle

### First sync
- Sync copies manifest-declared files into the consumer repo
- Sync writes `.tooling-sync-manifest.lock`
- No stale-file deletion occurs on first sync because no prior lock baseline exists

### Subsequent syncs
- Sync refreshes all manifest-declared files
- Sync compares the previous lock file with the current manifest
- Files that were previously managed but are no longer in the manifest become stale-file candidates
- By default, those stale managed files are removed and reported as `REMOVED: <path>`

**Exception:** `docs/REFERENCE/IMPROVEMENTS.md` is preserved in consumers even if it
appears in a prior lock after being removed from the manifest. This enables
non-destructive migration from tooling-managed to consumer-owned usage.

### Non-destructive rollout mode
If you want to inspect stale-file candidates before deleting them:
- run sync with `--no-delete`, or
- set `SYNC_NO_DELETE=1`

In that mode, stale managed files are preserved and reported as:
- `SKIPPED REMOVAL (--no-delete): <path>`

## Safety Rules

- Only files listed in the **previous lock** are ever candidates for stale-file deletion
- User-created files that were never managed by sync are never removed
- Unsafe stale paths (for example `../escape.txt`) are skipped with a security warning
- Symlinked stale targets are skipped with a security warning instead of being deleted
- Drift validation treats missing/invalid lock state as a contract problem, not a normal missing-file case

## Updating `scripts/sync_tooling.sh` in Consumer Projects

When `scripts/sync_tooling.sh` changes in tooling:
1. Consumer projects do **not** receive it automatically
2. Manual update is required
3. Review the script before copying because it is bootstrap/security-sensitive

This intentional exception prevents a compromised tooling source from silently
changing the script that controls future sync behavior.

## Practical Workflow

1. Commit tooling changes first
2. Update `.tooling-sync-manifest.toml` when the managed-file set changes
3. Sync consumer repos
4. Re-run `make drift-check`
5. If you need to inspect stale-file removals before applying them, repeat sync with `--no-delete`
6. Commit the resulting managed files + lock updates in the consumer repo
